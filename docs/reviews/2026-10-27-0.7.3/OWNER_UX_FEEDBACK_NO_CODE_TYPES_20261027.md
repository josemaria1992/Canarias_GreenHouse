# UX-07 — equipment types without code

## Owner request and verified current problem

Owner: “When creating an equipment type, there are still templates. I don't want the operator to have to understand the code. Is there any other way to create the types much more simple and intuitive?”

**Confirmed requirement:** an operator must be able to create and edit supported equipment types without reading/writing JSON, schema keys or programming enums. Existing type availability and editor-persistence fixes do not satisfy this requirement.

Verified at `8dc47b6` (application implementation unchanged since `de3088a`): `src/aquacrop/web/equipment.js:304–321` implements `typeEditor` as a JSON textarea, `JSON.parse` and an instruction listing OUTPUT/INPUT, DIGITAL/ANALOG and COMMAND/RUNNING/FAULT. Both New type and Edit call it. Type cards at `:340–341` also display internal operation/simulation enums. The interface still expects technical schema knowledge.

## Approved guided form, symbol previews and relevant questions

The owner has now explicitly approved following Codex's guided-form recommendation and added: “I want to be able to preview all the symbols when I am going to choose, and I should be asked relevant questions to fulfil the needs of that equipment.” The owner also asked how to add a need absent from the initial questions. The supported-feature extension below elaborates the existing Add property / Add signal proposal. The unsupported-feature request route remains a recommendation; its recipients, notifications and approval rules have not been decided. Approval of this UI does not change operating permissions or authorize new hardware behaviours.

1. **Choose what the equipment is.** Visual choices with names: Pump, Valve, Tank, Flow meter, Level sensor, other supported sensors, Water source, Sector, or a custom type. Offer “Copy an existing type” as a convenient starting point. Built-in definitions may remain internally; choosing Pump must not open its JSON or require the operator to learn what a software template means.
2. **Name and appearance.** Name, short optional description and a visual gallery of every available symbol/icon, with capitalized names, clear selection and an enlarged selected preview. Show the equipment-kind choices visually too. Do not offer a names-only selector or require saving to see the result. Preview the actual symbol used by Overview and Twin, including connection points and orientation where relevant; a decorative thumbnail alone does not establish how the equipment will appear in the diagram. Use the shared symbol/icon source so preview, saved equipment, Overview and Twin agree. If an icon is unavailable for a given diagram representation, explain that rather than showing a preview the renderer cannot honour. Tank type previews can be representative and labelled as such; actual tank size follows the capacity entered for each equipment item. Generate internal keys; do not expose schema syntax or require users to invent role identifiers. Keep hydraulic function separate from the decorative icon: changing an icon never adds ports or changes equipment behaviour. A type describes a reusable kind; a named equipment item remains on Equipment.
3. **Ask only relevant questions.** Pump example: Start/stop control; Does it report running? Does it report a fault? Valve example: Open control, any supported close control and position feedback. Sensor example: What does it measure? Which unit? What signal does it use? Use checkboxes, dropdowns and labelled number fields. Show physical signal choices such as 4–20 mA only where relevant, with a short explanation. Never invent wiring, active contact polarity, calibration or feedback that is not confirmed.
4. **Relevant properties and limits.** Show units and explain each required value next to its field. Tank capacity belongs to each tank item; defining a Tank type must not force all its equipment to share the same capacity. If a custom type needs additional properties or signals, provide an “Add property / Add signal” form with suitable validation; unsupported hardware must be explained rather than simulated as working.
5. **Review in ordinary language, then save a draft.** Example: “Irrigation pump — Start/stop output; running signal; fault signal; maximum running time: [entered value].” Name missing fields and how to fix them. Keep actual channel assignment/verification in the equipment/commissioning journey. A type draft must not assign channels, verify wiring, activate itself, enable a program or operate equipment.

Apply the same form to **editing existing types**, not only creation. Put uncommon technical settings in a clearly labelled expandable section using normal controls. JSON must never be a required workaround for custom supported types. If a developer-only raw view is retained, its existence/access is a separate product choice; do not expose it as the operator's normal editor or change permissions without agreement.

## When the initial questions miss a need

Keep the common form short, with one discoverable **Add a feature** action. Selecting it opens a plain-language choice of supported additions and asks the relevant follow-up questions:

- **A reading:** for example temperature, pressure or flow. Ask its label, unit and compatible signal/interface; guide measurement settings through the existing equipment configuration. It must appear as a usable reading in the existing downstream UI where supported, not merely as decorative text.
- **A status signal:** for example running, fault, valve position or another supported on/off status. Ask what the signal means and any required polarity/verification settings; do not silently assume contact wiring. Generate its internal role key. Only offer behaviours actually supported by the runtime for that kind.
- **A property:** for example manufacturer, rated flow or another equipment detail. Ask its label, value type (number, text, yes/no or choice), units when applicable and whether it must be filled in. Distinguish a manually entered property from a live measurement. A “maximum temperature” property alone does not implement an automatic stop: an enforced limit/condition must use the existing appropriate safety configuration explicitly.

Show added features as editable/removable rows before saving; update the ordinary-language summary. Preserve stable keys when editing, check duplicate names/keys and incompatible combinations, and explain any removal's effect on existing equipment before applying the established version/upgrade flow. Do not make operators use JSON for extra supported features.

**If the software cannot support the requested feature or behaviour:** say exactly what is unsupported, preserve the form, and let the user describe the missing need for review. This is a product/software extension, not an arbitrary text field that secretly controls hardware. For example, naming a second control output must not imply the engine knows how to operate a new reversible actuator. A request may be drafted without operating anything; do not claim it was sent, approved, implemented or simulated. Before implementing automatic request delivery, ask the owner where requests should go and who should review them; do not invent a recipient or approval route. Keep supported type creation usable independently.

## Implementation boundaries and acceptance

- Reuse the existing TypeBody model, draft/version endpoints, built-in definitions, validation and permission checks. Generate the validated definition from the form; do not create a parallel schema or a second type store. Preserve administrator activation and immutable versions; do not silently upgrade existing items.
- Load all supported fields into the form and preserve fields a simpler view does not display. Do not lose custom roles, property definitions, simulation configuration or limits on a no-change edit. Explain unsupported legacy settings before saving rather than dropping them. Never create fabricated simulation behaviour; retain NOT MODELLED with a plain explanation when no model exists.
- Keep unsaved entries, selection, focus and the open editor across refreshes and validation failures. Retain the UX-06 stable editor identity fix. Use field-level messages; remove raw enum/schema help from the everyday flow.
- Demonstrate in a browser, on copied data: create/edit a Pump with optional running/fault signals; a passive Tank with no channel; a Flow meter and Level sensor with the right measurement choices; a custom supported type with an extra property/signal. Preview every available icon/symbol before choosing, check selected preview against the saved Overview/Twin representation, and retain the selection through refresh/reopen. Exercise Add a feature, its follow-up questions and an unsupported request without losing entries or producing operational behaviour. No JSON input in any journey. Reopen drafts and verify meaning is preserved; verify a second edit does not erase hidden supported fields, and activation still follows current permissions/version rules.
- Keep scope focused: this improves Equipment types; it does not reintroduce equipment creation in Blocks or duplicate the Digital Twin drawing workspace. Use the approved short guided form with relevant follow-ups; routine layout choices can follow existing conventions. Ask about materially new behaviour, hardware needs or request-routing decisions rather than assuming them.
